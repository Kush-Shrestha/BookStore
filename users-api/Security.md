# Security Report: users-api 

## 1. OWASP Top 10 (2021) coverage

| # | Risk | How users-api defends against it |
|---|------|----------------------------------|
| A01 | Broken Access Control | Every `/users` route requires a valid access token (`authenticate`), then role checks (RBAC) and ownership checks (ABAC) so a customer can only read or edit their own profile. Admin-only routes are protected by `requireRole('admin')`. |
| A02 | Cryptographic Failures | Passwords are hashed with scrypt and a random salt, JWTs are signed with a secret of at least 32 characters, and Helmet sends HSTS so browsers use HTTPS only. |
| A03 | Injection | Zod strict schemas allow-list every field and reject non-string values (such as `{"$ne": null}`), script characters in names, and unknown keys. The in-memory store has no SQL; parameterised queries will be used in Unit 3. |
| A04 | Insecure Design | Login attempts are rate limited per IP and email, refresh tokens rotate with reuse detection, and registration cannot set a role. |
| A05 | Security Misconfiguration | Helmet sets the security headers, `X-Powered-By` is removed, CORS uses an allow-list instead of `*`, and errors use Problem Details without stack traces. |
| A06 | Vulnerable and Outdated Components | `npm audit` reports 0 vulnerabilities, a lock file pins versions, and Dependabot alerts and security updates are enabled on the repository. |
| A07 | Identification and Authentication Failures | Password rules (8 to 72 characters, letter and digit), a login limit of 5 failed attempts per 15 minutes per IP and email, and the same error message for a wrong password and an unknown email. |
| A08 | Software and Data Integrity Failures | JWT signature, issuer and audience are verified with a pinned algorithm, and dependencies are installed from the lock file. |
| A09 | Logging and Monitoring Failures | Each request gets a request ID and is logged. Alerting and monitoring are not built yet and are planned for Unit 4. |
| A10 | Server-Side Request Forgery | The API never fetches a URL supplied by a user. The GitHub URLs are hard-coded and S3 keys are generated by the server. |

## 2. A weakness that is still left

Rate-limit counters are stored in the memory of one Node process. Each instance counts separately and a restart resets the counters, so an attacker could spread requests across several instances behind a load balancer, or wait for a restart, to get more attempts. **Fix:** move the counters to a shared store, for example Redis with `rate-limit-redis`, so all instances use the same limits.

## 3. Short answers

**Why does CORS not protect the API from curl or a server-side attacker? What does?**
CORS is enforced by the browser. It only decides whether JavaScript on another website may read a response, and it is the browser that blocks it. A tool like curl or a server-side script never checks CORS headers, so it can send any request it likes. The API itself must be protected by authentication (tokens), authorization (RBAC and ABAC), input validation and rate limiting, which apply to every client.

**Our /users routes use Bearer tokens and /auth/refresh uses a cookie. Why does only the second need CSRF protection?**
Browsers attach cookies to requests automatically, even when the request is started by another site, so an evil page can make a logged-in user's browser call `/auth/refresh` with the cookie included. A Bearer token must be added by JavaScript in an `Authorization` header, and a foreign site cannot read it or add it for the user. Because of this, the `/users` routes cannot be forged cross-site, while the cookie route needs the Origin check, the SameSite cookie and the JSON-only requirement.

**Why is allow-listing (the name regex) safer than block-listing?**
An allow-list describes exactly what is valid, such as letters, spaces, apostrophes, dots and hyphens, and rejects everything else, including attacks nobody has thought of yet. A block-list only rejects the bad strings it knows about, so an attacker can bypass it with variations such as `<img onerror=...>`, different casing or encodings. Allow-lists fail safe, while block-lists fail open.
